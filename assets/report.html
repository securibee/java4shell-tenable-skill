Limits of the data

What Tenable data can't see

Exposure needs four things at once: an affected Java build, x86-64, a CPU that exposes AVX-512 VBMI, and the JVM's Base64 intrinsic left on. Tenable reports the Java build when its plugin output can be read, and the architecture only for some hosts. It can rule a CPU out by model, but never confirm one.

Tenable's plugins don't report CPU feature flags or a running JVM's flags yet, so installs on affected builds show as "Affected build – CPU unconfirmed" until they do.

"Unknown – verify" means Tenable data could not settle the build itself: a version string that is ambiguous at the fixed build, plugins that disagree on the version, a plugin output that was not retrieved or was cut off before all its installs, or a Tenable CVE plugin that flags an asset the version rules would clear. A mitigation option seen on a process command line is shown as evidence only; confirm it on the running JVM with jcmd.

Interim mitigations

Patch to the vendor's fixed build. Until then, these JVM options keep the vulnerable path off.

  • -XX:-UseBASE64Intrinsics (preferred: turns off only the accelerated Base64 path).
  • -XX:UseAVX=2 (turns off AVX-512; x86-64 only, Java on ARM64 will not start with it).
  • Do not use -XX:DisableIntrinsic=_base64_decodeBlock: without -XX:+UnlockDiagnosticVMOptions the JVM will not start.
  • Confirm on the running JVM with jcmd <pid> VM.flags -all, and remove the option after patching.
